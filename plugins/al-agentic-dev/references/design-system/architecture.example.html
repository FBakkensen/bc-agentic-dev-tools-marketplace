Item charge allocation, validated at posting.

Three modules cooperate under a strict read → process → write discipline. The feature touches BaseApp at exactly one place — event subscribers on the Sales-Post codeunit.

Goal

Catch item charge allocation mismatches at posting time before the invoice posts, surface the cause inline on the document, and produce a deterministic audit trail tying each allocation back to its source line.

R → P → W boundary

Posting Subscribers is the only module that writes; everything else reads or processes. This is the boundary that protects the BaseApp posting routine.

Reads sit on the released document. Charge Validation opens the Sales Header by No., iterates the Sales Line rows it owns, and resolves each related Item Charge Assignment (Sales) row. Reads never reach outside the document — neither for journal templates nor for posting setup. That keeps the read layer trivially testable: it depends only on records that already exist on the released document.

Processing is pure. Allocation Resolver takes the collection of read rows and produces an in-memory graph that maps each charge to its receiving lines. The resolver has no AL Insert or Modify calls — it returns a value object. The validator on the same module inspects the graph, reports balanced/imbalanced, and surfaces the specific lines responsible. Everything in the process layer is reproducible from inputs; the resolver could be replayed against an archived document and produce identical output.

Writes go through BaseApp. Posting Subscribers hosts the only AL code that touches a table outside our feature schema. It subscribes to OnAfterCheckSalesDoc and OnBeforePostSalesDoc from Sales-Post, calls the validator, and on success lets posting proceed; on failure it surfaces the error and aborts. Audit entries land via Insert against our own table — that write is not a BaseApp extension.
